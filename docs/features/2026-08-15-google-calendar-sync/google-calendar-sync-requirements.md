# 요구사항: Google Calendar 완전 양방향 동기화

> **모드**: Socratic (자유 형식). 다음 단계의 `tech-design` 이 본 문서를 자유 형식 산문으로 읽습니다 (PRD 6 섹션 ID 강제 X).
>
> **다음 단계 안내**: 이 문서는 기획 레벨 요구사항입니다. 스키마·클래스·API 호출 설계는 `google-calendar-sync-tech-design.md` 에 들어갑니다.

## 1. 배경 — 지금은 "동기화" 가 아니다

코드 조사 결과, 현재 구현은 **일방향·일회성 "생성 시 등록"** 한 가지뿐입니다.

| 구간 | 현재 상태 |
|---|---|
| 할 일 **생성** → 캘린더 | ✅ 동작 (`add_todo_controller.dart:129-149`, `s.addToCalendar && s.dueAt != null` 일 때만) |
| 할 일 **수정** → 캘린더 | ❌ **미배선**. `TodoActionsController.update` 가 캘린더를 전혀 건드리지 않음 → 날짜를 바꿔도 구글 이벤트는 옛날 그대로 |
| 할 일 **삭제** → 캘린더 | ❌ **미배선**. 캘린더에 고아 이벤트가 영구히 남음 |
| 할 일 **완료** → 캘린더 | ❌ 없음 |
| 캘린더 → 할 일 (역방향) | ❌ 전무. OAuth scope 자체가 `calendar.events` 하나뿐이라 캘린더 목록 조회도 불가 |
| 연결/해제 UI | ❌ 없음. `signOut()` 은 구현돼 있으나 앱 전체에서 호출자 0건 |

`CalendarService.updateEventForTodo` / `deleteEvent` / `tryCreate·Update·DeleteCalendarEvent` 는 **전부 작성돼 있으나 호출자가 없는 dead code** 입니다. `IMPLEMENTATION_PLAN.md §8` 은 이 항목들을 `[x]` 로 표시하고 있어 **계획서와 실제 코드가 불일치** 합니다.

가장 나쁜 것은 **오도하는 UI** 입니다 — 편집 시트(`add_todo_sheet.dart:955-969`)는 날짜가 있으면 "Google Calendar 에 등록" 토글을 보여주지만, `_applyEdit()` 은 그 값을 읽지 않습니다. 대표님이 토글을 켜도 아무 일도 일어나지 않습니다.

### 이미 갖춰진 것 (배선만 하면 되는 자산)

- `Todo.calendarEventId` — 도메인 / Drift(v1부터) / Supabase 3계층에 **이미 존재**
- `CalendarService.buildEvent` — 날짜 모드 5종(none/allDay/startTime/endTime/range) 매핑 + 반복 RRULE 생성, 테스트 3파일 보유
- 플랫폼별 인증 분리 — macOS `googleapis_auth` 데스크톱 플로우 / Android `google_sign_in` + `serverClientId`, Google Console 설정 2026-08-09 완료
- **outbox 패턴** — Supabase 동기화가 local-first + outbox + 재시도로 이미 검증됨. 캘린더도 같은 뼈대를 쓸 수 있음

## 2. 대표님이 확정한 범위

| 질문 | 대표님 답 |
|---|---|
| 동기화 방향 | **C — 완전 양방향.** 앱↔캘린더 양쪽 변경이 서로 반영되고, 구글 캘린더에서 **새로 만든 일정도 앱에 할 일로 들어온다** |
| 대상 캘린더 | **3 — 설정에서 지정.** 쓰기 캘린더 1개(기본 primary) + 읽기 캘린더 다중 선택 (auto 위임에 따라 자동 확정) |
| 진행 방식 | 요구사항 → 기술설계 → 구현계획 → 실행까지 auto |

## 3. 핵심 결정

각 결정은 대안을 검토한 뒤 하나를 채택했고, 채택 근거를 함께 적습니다.

### D-1. 동기화 트리거는 "저장되는 모든 순간"

할 일이 바뀌는 **모든** 경로에서 캘린더가 따라갑니다. 등록/수정만이 아니라 삭제·타입 전환·완료까지 포함합니다.

- 편집 시트의 자동 저장(닫힘=저장)도 트리거에 포함 — 대표님 앱은 배경 탭·드래그·Esc 전부 저장으로 동작하므로, 여기서 누락되면 "가끔 반영 안 됨" 이 됩니다
- 편집 시트 진입점 7곳(홈/카테고리/상세/검색/아웃라인 2곳/타임라인)이 **모두 `todoActionsProvider` 를 경유**하므로, 훅 지점은 한 곳으로 수렴 가능합니다

### D-2. 캘린더 대상은 설정에서 지정 (쓰기 1 + 읽기 N)

- **쓰기 캘린더 1개** — 앱이 만드는 이벤트가 들어갈 곳. 기본값 `primary`
- **읽기 캘린더 N개** — 체크박스 다중 선택. 기본값은 쓰기 캘린더 하나만 ON
- 현재 `'primary'` 하드코딩(`calendar_service.dart`)을 설정값으로 교체

*대안 검토*: 전용 캘린더 `하루` 자동 생성안은 유입 범위가 깔끔하지만, 대표님이 C(완전 양방향)를 고르신 이상 **기존 개인 일정도 앱에서 보시겠다는 의도**로 읽었습니다. 전용 캘린더는 그 의도를 막습니다. 지정 방식이면 대표님이 나중에 전용 캘린더를 만들어 그것만 켜는 것도 가능해 상위 호환입니다.

### D-3. 유입 필터 — 기본은 "내가 만든 일정만"

읽기 캘린더를 켜는 순간 남이 초대한 회의까지 할 일 목록에 쏟아지면 앱이 망가집니다. 그래서:

- **기본**: 내가 주최자(organizer)이거나 내가 만든 이벤트만 할 일로 유입
- **설정 토글**: "초대받은 일정도 가져오기" (기본 OFF)
- **항상 제외**: 거절(declined)한 이벤트, 종일 반복 생일/공휴일 캘린더

### D-4. 유입된 일정의 카테고리는 캘린더별로 매핑

구글에서 들어온 일정도 앱에서는 할 일이므로 카테고리가 있어야 합니다.

- 읽기 캘린더마다 "이 캘린더의 일정은 → [카테고리] 로" 를 설정에서 지정
- 미지정 시 기본 카테고리 하나로 (대표님이 설정에서 선택, 초기값은 기존 기본 5종 중 첫 항목)
- 대표님 카테고리는 v1.2 부터 동적이므로, 매핑 대상 카테고리가 삭제/보관되면 기본 카테고리로 자동 폴백

### D-5. 삭제의 의미는 "그 할 일이 어디서 왔는가" 로 갈린다

| 상황 | 동작 |
|---|---|
| 앱에서 할 일 삭제 | 연결된 캘린더 이벤트도 삭제 |
| 캘린더에서 이벤트 삭제 — 그 할 일이 **앱에서 만든 것** | 할 일은 **유지**, 일정 연결만 해제 (데이터 손실 방지) |
| 캘린더에서 이벤트 삭제 — 그 할 일이 **캘린더에서 유입된 것** | 할 일도 **삭제** (원본이 사라졌으므로) |
| 할 일 → 메모로 타입 전환 | 연결된 이벤트 삭제 (현재는 로컬 링크만 끊고 고아 이벤트를 남김 — 결함) |

이를 위해 할 일마다 **출처(앱 생성 / 캘린더 유입)** 를 기록해야 합니다.

### D-6. 완료는 캘린더에서 "색"으로 표시

완료 토글이 캘린더에 반영되지 않으면 캘린더만 보고는 처리 여부를 알 수 없습니다.

- 완료 시 이벤트를 **회색 계열 색상으로 변경**, 미완료로 되돌리면 원래 색 복구
- **제목은 건드리지 않습니다** — "✓" 프리픽스 방식은 역방향 가져오기에서 제목 파싱 문제를 낳습니다
- 완료해도 **이벤트를 삭제하지 않습니다** (대표님 앱의 "완료는 히스토리 보관" 원칙과 일치)

### D-7. 충돌은 최종 수정 시각 우선(LWW), 동률이면 앱 우선

같은 항목이 앱과 캘린더에서 동시에 바뀌면 `updatedAt` 과 이벤트의 `updated` 중 **나중 것**이 이깁니다. 완전히 같으면 앱을 신뢰합니다. 이는 기존 Supabase 동기화의 LWW 규칙과 같은 방식이라 대표님이 이미 익숙한 동작입니다.

### D-8. 자기 반향(echo) 은 반드시 차단

앱이 쓴 변경이 되돌아와 다시 앱을 갱신하고 또 캘린더로 나가는 무한 루프는 이 피처의 가장 큰 사고 위험입니다. 앱이 쓴 이벤트에는 앱 서명(할 일 id + 리비전)을 남기고, 되가져올 때 **자기가 쓴 리비전이면 무시**합니다.

### D-9. 되가져오기는 증분 방식 + 명시적 타이밍

- 전체 목록을 매번 훑지 않고 **증분 동기화 토큰** 기반으로 "지난번 이후 바뀐 것"만 가져옵니다
- 트리거: 앱 시작 / 포그라운드 복귀 / 사용 중 주기(기본 5분) / 당겨서 새로고침
- 실시간(5초 이내)은 Supabase 동기화에만 적용되는 기준이며, 캘린더에는 적용하지 않습니다 — 구글 API 쿼터와 배터리를 고려한 판단입니다

### D-10. 반복 일정은 기존 설계 유지

- 앱 → 캘린더: 반복 마스터가 RRULE 이벤트 1개를 소유, 개별 인스턴스는 이벤트를 만들지 않음 (`date-repeat` 피처에서 확정된 설계)
- 캘린더 → 앱: 반복 이벤트는 앱에서 **반복 마스터 할 일 1개**로 유입
- 캘린더에서 특정 회차만 옮긴 예외 인스턴스는 **v1 범위 밖** (§6)

### D-11. 연결 해제 시 캘린더 이벤트는 남긴다

설정에서 "연결 해제" 하면 토큰만 폐기하고, 이미 만들어진 구글 이벤트와 링크(id)는 그대로 둡니다. 재연결하면 기존 링크가 그대로 살아납니다. 대표님 캘린더의 일정을 앱이 마음대로 지우지 않는 편이 안전합니다.

### D-12. 오프라인·실패는 큐에 쌓고 재시도

기존 Supabase outbox 와 동일한 방식으로, 캘린더로 나갈 변경도 큐에 넣고 성공할 때까지 재시도합니다. 비행기 모드에서 할 일을 고쳐도 온라인 복귀 시 캘린더가 따라옵니다.

## 4. 인터랙션 흐름

### 4-1. 최초 연결
1. 설정 → "Google Calendar" → **[연결]**
2. macOS: 브라우저 동의 화면 / Android: 계정 선택 + 권한 동의
3. 연결되면 계정 이메일과 함께 **캘린더 목록**이 뜸
4. 쓰기 캘린더 1개 선택(기본 primary), 읽기 캘린더 체크
5. 첫 동기화 실행 → 결과 요약 ("N건 가져옴")

### 4-2. 할 일 등록
- 날짜/시간을 넣으면 캘린더 토글이 나타남 (현행 유지)
- **개선**: 토글 상태가 기억됨 (현재는 시트를 열 때마다 매번 OFF로 초기화)
- 저장 즉시 이벤트 생성, 실패 시 큐에 적재 + 안내

### 4-3. 할 일 수정 (핵심 결함 구간)
- 제목·날짜·시간·기간·종일 여부·반복 규칙 변경 → **연결된 이벤트가 즉시 따라감**
- 날짜를 지우면 → 이벤트 삭제 + 링크 해제
- 날짜가 없던 할 일에 날짜를 넣고 토글을 켜면 → 이벤트 신규 생성
- 편집 시트의 캘린더 토글이 **실제로 동작함** (지금은 무효)

### 4-4. 할 일 삭제 / 완료
- 삭제 → 이벤트 삭제 (D-5)
- 완료 → 이벤트 색상 회색 (D-6)

### 4-5. 캘린더에서 바꾼 경우
- 구글 캘린더에서 시간을 드래그하거나 제목을 고치면 → 다음 동기화에 앱 할 일에 반영
- 구글 캘린더에서 이벤트를 지우면 → D-5 규칙대로 처리

### 4-6. 캘린더에서 새로 만든 경우
- 읽기 캘린더에 내가 만든 새 일정 → 앱에 할 일로 등장 (카테고리는 D-4 매핑)
- 유입된 할 일은 앱에서 **"캘린더에서 가져옴"** 을 알아볼 수 있어야 함

### 4-7. 오프라인 / 실패
- 큐에 쌓고 재시도, 대기 건수를 설정 화면에서 확인 가능
- 권한 만료·거부 시 재연결 안내

## 5. 우려와 해결

| 우려 | 해결 |
|---|---|
| **무한 루프** (앱→캘린더→앱→…) | D-8 앱 서명 + 리비전 비교로 자기 변경 무시. 이 피처 최대 위험이므로 테스트 필수 |
| **개인 일정 폭주** — 회의 초대까지 할 일이 됨 | D-3 기본 "내가 만든 일정만", 거절 이벤트 제외, 읽기 캘린더 기본 1개 |
| **두 기기 중복 생성** — macOS/Android 가 같은 할 일로 이벤트를 각각 만듦 | 이벤트 id 가 Supabase 로 동기화되므로, 이미 id 가 있으면 생성 대신 갱신. 경합 구간은 LWW 로 수렴 |
| **OAuth scope 부족** | 현재 `calendar.events` 만으로는 캘린더 **목록** 조회가 불가. scope 확대가 필요하고, **기존 사용자는 재동의가 필요**함 |
| **Supabase 마이그레이션 누락** | HANDOFF.md 기준 `end_at`/`is_all_day`/`time_anchor`/`started_at` 마이그레이션이 **아직 미실행**. 이번에 컬럼이 더 늘어나므로 SQL 재실행이 **대표님 액션 항목**. 미실행 시 PGRST204 로 동기화 전체가 죽음 |
| **기존에 등록된 이벤트** | `calendarEventId` 가 이미 있는 할 일은 링크를 그대로 인정. 재등록하지 않음 |
| **토큰 평문 저장** (macOS) | 기존 결정(ad-hoc 서명 환경에서 키체인 사용 불가, 1인 개인 앱 전제) 유지. 이번 피처에서 바꾸지 않음 |
| **API 쿼터** | 증분 토큰 + 5분 주기로 호출량 억제. 토큰 만료(410) 시 전체 재동기화 1회 |

## 6. 범위 밖 (Out of Scope)

- **반복 이벤트의 개별 인스턴스 예외** — 캘린더에서 특정 회차만 옮기거나 지운 경우의 정밀 반영
- **참석자·초대·회의실·화상회의 링크** 관리 (읽어서 보여주는 것도 v1 제외)
- **알림(reminder) 동기화** — 구글 알림 설정과 앱 알림의 연동
- **첨부파일·위치 정보** 동기화
- **캘린더 생성/삭제** — 앱이 구글 캘린더 자체를 만들거나 지우지 않음 (선택만 함)
- **여러 구글 계정 동시 연결** — 계정 1개만
- **팀 공유/타인 캘린더 쓰기** — 비전의 "개인 전용" 원칙에 따라 제외
- **웹훅(push notification) 기반 실시간 수신** — 서버가 필요하므로 제외 (백엔드 없음이 프로젝트 전제)
- **iOS / 웹** — 비전에서 이미 제외

## 7. 수용 기준

1. 할 일의 **제목·날짜·시간·기간·종일·반복**을 수정하면 연결된 구글 이벤트가 따라 바뀐다 (편집 시트 진입점 7곳 전부)
2. 할 일을 삭제하면 구글 이벤트가 사라진다. 고아 이벤트가 남지 않는다
3. 할 일에서 날짜를 지우면 이벤트가 삭제되고 링크가 해제된다
4. 할 일 → 메모 전환 시 이벤트가 삭제된다
5. 완료 토글이 구글 캘린더에서 색으로 구분된다
6. 구글 캘린더에서 시간을 옮기면 앱 할 일의 시간이 바뀐다
7. 구글 캘린더에서 새 일정을 만들면 앱에 할 일로 나타나고, 지정한 카테고리로 들어간다
8. 캘린더에서 이벤트를 지웠을 때 D-5 표의 4가지 경우가 표대로 동작한다
9. 앱↔캘린더 왕복이 **무한 루프를 만들지 않는다** (한 번 반영 후 정지)
10. 설정에서 **연결 / 해제 / 계정 확인 / 쓰기·읽기 캘린더 선택 / 카테고리 매핑 / 마지막 동기화 시각**을 볼 수 있다
11. 오프라인에서 수정한 내용이 온라인 복귀 후 캘린더에 반영된다
12. 캘린더 연동을 끄거나 연결하지 않은 상태에서도 **앱의 모든 기존 기능이 그대로 동작한다** (연동은 부가 기능)
13. macOS 와 Android 양쪽에서 동일하게 동작한다 (기능 parity)
14. 편집 시트의 캘린더 토글이 실제 효과를 갖는다 (오도 UI 제거)
